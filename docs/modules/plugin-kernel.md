# 插件内核

让每项能力都以插件形式提供：按依赖自动激活，注册的一切都能撤销，停用前先安全收尾。借鉴 dsh（DeepSeek Harness）及其所用 Cordis 框架的模式，自研最小实现，不引入 Cordis 依赖（D-13、D-14）。P0 实现。

## 职责

- 加载、激活、停用和热替换插件。
- 维护服务目录：谁提供了什么服务、谁依赖它。
- 管理插件的全部注册（服务、事件监听、定时器、子进程、连接），停用时按序撤销。
- 按 profile 组合启用哪些插件、用什么配置。
- 把 sidecar 进程包装成宿主内的服务提供方。

## 不负责

- **授权对外动作。** 由[安全核](safety-core.md)负责。插件内核只决定插件是否在运行，不决定它能否发声或输入。
- **沙箱隔离。** 同进程插件之间没有安全边界，第三方代码只能以 sidecar 接入（D-20）。
- **撤回已发生的外部效果。** 观众已经听到的话、已经发出的网络包都撤不回，所以停用要先经过“静止中”，由安全核确认物理效果已经停止。

## 核心概念

| 概念 | 含义 |
| --- | --- |
| 服务 | 占据一个稳定名字的能力，例如 `speech`、`stage`、`llm`、`memory`。使用方按名字查找，不导入具体实现 |
| 能力接缝 | 一项可替换能力由三个角色组成：定义接口的服务定义、实现它的提供方、使用它的消费方。替换提供方就能换掉整条能力，例如把模拟 TTS 换成真实 TTS |
| 插件 | 声明自己提供哪些服务、依赖哪些服务，并在激活时注册副作用的单元 |
| 注册 | 一切副作用（提供服务、监听事件、定时器、子进程、连接）都通过可撤销的注册完成，每个注册都返回对应的撤销函数 |
| profile | 一组有序的插件包加上 patch 文件，决定启用哪些插件、用什么配置 |

## 清单

每个插件有一份清单，在 P0 用 TypeBox 定义（R-03），即 JSON Schema（D-21）：

| 字段 | 含义 |
| --- | --- |
| `id`、`version` | 插件身份 |
| `tier` | `critical`（关键平面）或 `ordinary`（普通插件）。安全核不是插件 |
| `provides` | 提供的服务，形如 `tts@1` |
| `inject` | 依赖，形如 `stage@1`；可选依赖加 `?`（如 `memory@1?`），不阻塞激活，在用到时探测 |
| `permissions` | 申请的能力，例如 `speech.output`、`obs.scene`、`game.goal`、`game.input`、`net.egress:<主机>` |
| `process` | `in-process` 或 `sidecar` |
| `config` | 配置的 Schema；加载时先按 Schema 补齐缺省值再校验 |

服务按 `名字@主版本` 匹配，主版本不兼容时消费方停在 WAITING，并给出原因。

## 生命周期

```text
WAITING ──依赖齐全──► LOADING ──► ACTIVE ──停用或依赖消失──► QUIESCING ──► UNLOADING ─┬─ 依赖消失 ─► WAITING
   ▲                     │                                                          └─ 停用 ────► DISPOSED
   │                     └────────────── 加载失败 ──► FAILED ──退避重试──┘
```

- **服务在激活成功后才发布。** 插件只能取得 `inject` 中声明的服务、提供 `provides` 中声明的服务；激活结束时缺少任何声明的服务都按加载失败处理。
- **依赖是持续生效的。** 插件只在全部必需服务都存在时才运行。某个服务消失，依赖它的插件经过 QUIESCING 卸载，实例被丢弃，条目回到 WAITING；服务恢复后自动重新加载。这本身就是降级机制。
- **WAITING 必须说明原因**（缺哪个服务、哪个版本不兼容），并显示在操作台上。
- **FAILED**：按退避重试有限次数；仍失败则停在 FAILED，等待操作员处理。实例活动满一段时间才清零重试计数，避免崩溃循环无限重试。配置不符合 Schema 时直接停在 FAILED，不重试。
- **撤销顺序。** 同一插件的注册按“后注册先撤销”的顺序撤销。有顺序要求的清理放在同一个撤销函数里。

### 静止中（QUIESCING）

这是相对 Cordis 新增的状态。插件从 ACTIVE 停用时，先依次完成：

1. 停止接收新工作。
2. 安全核吊销该插件持有的全部执行许可；设备凭令牌拒绝其后续指令。
3. 对在途任务发出取消，并设截止时间。
4. 等待物理确认，例如已静音、游戏输入已全部释放。
5. 运行撤销函数。

超过截止时间仍未确认时：

- sidecar 插件：终止其进程。
- 进程内插件：强制运行剩余的撤销函数，丢弃实例。
- 两种情况都记录 `unknown` 并告警；若该插件属于关键平面，安全核同时执行急停路径。

## 事件分发

扩展点声明自己的分发模式，只能用对应方式分发：

| 模式 | 执行方式 | 返回值 | 异常 | 典型用途 |
| --- | --- | --- | --- | --- |
| 观察 | 按注册顺序同步调用，不等待异步监听者 | 无 | 捕获并记录，不影响其它监听者 | 遥测、日志 |
| 包装 | 环绕中间件，可异步；监听者调用 `next()` 交给下游，不调用即短路 | 有 | 向调用方抛出 | 改写请求、追加上下文 |
| 并行 | 并发调用全部监听者并等待全部结束 | 无 | 收集全部异常后一并报告 | 多路预热 |
| 串行 | 按注册顺序逐个等待，第一个非空返回值生效 | 有 | 向调用方抛出 | 选择一个提供方 |
| 首个决定 | 与串行相同，但只允许同步监听者 | 有 | 向调用方抛出 | 快速决策 |

涉及安全的扩展点不允许任意改写：在可改写的包装链之后，只运行“单调守卫”，它们只能拒绝或弃权。最终授权仍由安全核完成。

## 加载器与 profile

- profile 由有序的插件包和 patch 文件组成。条目的 `id` 是位置，`plugin` 是填在这个位置上的实现，另可带 `config`、`disabled` 与 `grant`（授予的权限）。
- patch 按条目 `id` 替换整条配置、插入新条目、设为 `disabled` 或重新启用。`disabled` 会保留条目，但卸载实例。
- 内置三个 profile：`sim`（全部外部服务换成种子驱动的模拟实现）、`dev`、`live`。
- 安全核不在 profile 里，任何 patch 都无法移除或禁用它。
- `pnpm run profile <profile> [patch…]` 打印展开并应用 patch 后实际生效的插件条目和配置。

## 热替换

- 普通插件：先加载并校验新版本（其服务暂不发布），再让旧实例经过 QUIESCING 卸载，然后发布新实例的服务；新版本加载失败就保留旧实例。这只是“类事务”，不保证原子：新旧实例会短暂并存，依赖方会经历一次停用与重新激活。
- 关键平面：只能在维护态替换。
- 安全核：永不热替换（D-19）。

## sidecar 代理

每个 sidecar 由宿主内的一个代理插件管理，代理插件用一个可撤销注册持有整个子进程：

```text
启动子进程 → 握手（协议版本、提供的服务与主版本、申请的权限）→ 健康检查 → 注册服务
```

- 子进程以 `sidecar.<条目 id>` 角色连接宿主；宿主先监听本机通道，再按 profile 加载插件。握手是 `sidecar.describe` 与 `sidecar.health` 两个 RPC：声明提供的服务须与清单一致，申请的权限须已授予，否则加载失败。Python sidecar 的健康检查另带本进程此刻的节流状态（`qos`，见 [Windows 平台](../platform/windows.md#定时与调度)）。
- 代理插件可以把 sidecar 的方法原样转发成服务，也可以适配成具体的服务接口，例如 TTS 代理把 `tts.synthesize` 与二进制音频适配成本地 TTS 引擎（见[发声](speech.md#本地-tts-sidecar)）。
- 握手不等重的初始化：sidecar 先完成握手、插件随即激活，模型加载等放在握手之后在后台进行，是否就绪由代理提供的服务自己报告（例如 TTS 引擎的 `ready`）。插件内核的激活时限不变，也不为此新增状态。
- 子进程退出或连接断开时，代理撤回其服务，依赖方自动回到 WAITING；代理按 FAILED 的退避重启子进程。
- sidecar 只返回数据，不直接驱动扬声器、OBS 或游戏。
- 停止方式：先发 RPC 关闭，再关 stdin 让子进程读到 EOF 后退出，超时再强制终止（R-06）；子进程在哪一步退出记入日志。
- sidecar 管住自己派生的进程（R-06）：Windows 上启动时先把自己放进设了 KILL_ON_JOB_CLOSE 的 Job Object，此后派生的全部子孙进程（含第三方库自己起的）都在其中，不能脱离；句柄不被继承、不主动关闭，sidecar 无论怎样退出它们都随之终止。其它平台跳过，派生的进程以 stdin 为生命线。
- Python sidecar 的运行时在 `python/bellis_sidecar`：本机通道客户端、JSON-RPC 对端、握手与停止、Job Object；消息模型由 `packages/protocol` 经 `pnpm run gen` 生成（D-21、R-24）。宿主直接启动 uv 工作区虚拟环境里的解释器，不经 `uv run`（见 [Windows 平台](../platform/windows.md#进程)），以 PYTHONPATH 指向各包的源码目录。

## 权限

宿主提供的核心服务可以按插件实例生成实现：每个实例拿到的安全核门面都绑定了它自己的实例编号，不能冒用其他实例的身份申请授权或持有许可。实例编号带本次启动的标识，重启后不与上次重复。

插件在清单里申请权限，安全核按 profile 授予；申请而未授予的权限使插件停在 WAITING 并说明原因。插件拿到的是收窄过的上下文，只能看到被授予的服务。这一层只防误用，不防恶意代码，所以第三方代码一律以 sidecar 接入。

外发按主机授权：插件只连接 profile 授予了 `net.egress:<主机>` 的主机。也可以写成 `net.egress:*.<域名>`，授予该域名下任意层级的子域名，不含域名本身（`*.chat.bilibili.com` 不授予 `chat.bilibili.com`）；`*` 只能出现在最前面，其它写法都是精确匹配，主机名不分大小写。清单按插件的缺省端点申请；端点可配置时（例如本机测试或改用其他区域的端点），插件在连接前自行核对端点主机已被授予，未授予即不连接并说明原因。

插件需要凭据（云端 TTS 的密钥、VTube Studio 的插件令牌）时，经宿主按实例提供的凭据服务（`secrets@1`）读写 SecretStore，只能访问 profile 授予它的条目，权限写成 `secret:<名字>`。会话连接信息与 OBS 凭据由宿主管理，授予了也拿不到。凭据的值不写日志、不进事件。按 Rule of Two（见[安全核](safety-core.md#执行闸门)），插件分两类授予：

- **解读观众输入或据此作决定的插件**（分诊、决策、投票等）不授予任何凭据。
- **只负责收发的接入插件**（弹幕接入、模型客户端、Iris 客户端、云端 TTS 等）只授予它自己那一家服务的凭据，不授予其它条目，也不授予 OBS 的连接与能力；收发的内容只当作数据转交，不当作指令解析。

宿主提供的 OBS 连接也按权限交出，凭据都留在宿主：

- `obs.control`：OBS 控制的连接（见 [Stage](stage.md#obs-控制)）。
- `obs.meters`：只读的音量表连接，只订阅 InputVolumeMeters，只能读输入的音频同步偏移，发不出控制请求（见 [Stage](stage.md#对齐)）。它改变不了 OBS，不是对外动作，不经执行闸门；也不是 Rule of Two 所说的 OBS 管理能力，安全核的禁止能力清单不变。

## 验收（P0）

- 依赖消失时，消费方经过 QUIESCING 回到 WAITING；依赖恢复后重新激活。
- sidecar 崩溃后服务被撤回，依赖方回到 WAITING，重启后恢复。
- profile 和 patch 能启用、禁用、替换插件，且无法禁用安全核。
- 普通插件热替换失败时回退到旧实例。
- QUIESCING 在物理确认超时后，按上述规则终止或强制撤销，并记录 `unknown`。
