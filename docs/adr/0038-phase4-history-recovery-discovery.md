# ADR 0038：持久恢复发现与宿主取消归属

状态：恢复发现、宿主生命周期联动及真实安装验证已完成；自动后台恢复及完整解除未完成。日期：2026-09-07。

ADR 0037 的维护调度要求调用者持有原 runId，且隐私变更前需自行传递取消。新增 DB Worker 的范围恢复状态读取及 `Phase4HistoryRevalidator.resume()`，并由 `Phase4MemoryHost.historyRevalidator(verifier)` 创建绑定宿主身份和取消生命周期的调度器。

恢复读取在一个本地事务快照中返回所选 scope/provider 的缺口、策略、真实隐私 blocked 状态和原清单。它验证缺口正文摘要与身份，并区分 absent、current 和 stale：current 必须通过完整原清单/来源核对；正常策略或来源变化导致 stale；损坏的缺口、来源或清单摘要直接报错。读取不替换任何清单，也不解除缺口。

`resume()` 不接收猜测的 gapId/generation/runId。它从持久状态发现这些身份，复用 current 清单；只有缺失或正常失效的清单才选择新 run。旧清单的替换仍经过原事务核验，读取后的并发变化会被拒绝。真实隐私 blocked、无所选 Provider 缺口及身份不符均不发起核验。相同实例的恢复发现与后续全部工作共同占用一个有界在途名额。

宿主工厂固定配置中的 scope/provider/agent/space，拒绝未注册的 Verifier 和已关闭的宿主。创建的调度器绑定当前宿主代际；隐私、Forget、资源/Persona 失效、Session 改绑及停止沿用 `invalidate()` 路径，先取消旧维护任务，再执行后续持久变更或关闭。旧调度器不能跨代际重新开始；新任务必须由宿主重新创建。运行中的历史屏障转移尚未完成时也不能创建维护任务。

正常 MemoryHost 因缺口启动失败后，其生命周期已关闭，不能重新启用。可信维护装配可新建一个未启动普通 Provider/Persona 的 MemoryHost，仅通过工厂创建恢复调度器，最后关闭它。这条路径无需绕过正常启动屏障，也不启动普通 Context、SSE 或 Outbox。

此处是同一宿主对象内的取消归属。其他进程直接改变数据库或远端权限，仍依赖发送前准入、请求取消和结果落盘时的复核；没有把本地检查宣称为覆盖 HTTP 的跨进程锁。自动重试/后台唤醒、其他事实的公开核验、旧策略请求再授权、跨批次一致性与安全解除继续实施。

最终根检查通过 1049 项单元/性质测试、266 项集成测试，168 个生成契约无漂移；专项持久化八项和 Runtime 六项通过。最终 Core/Chromium 联合探针通过宿主工厂、持久发现和重启复用，工具及既有 24 组恢复冒烟通过，完整恢复入口保持退出 2。见 [本轮证据](../evidence/phase4-history-recovery-discovery-probe.json)。
