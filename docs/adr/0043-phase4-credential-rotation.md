# ADR 0043：凭据轮换与原事实恢复

状态：受控轮换及真实安装验证已完成。日期：2026-09-07。

ADR 0041 的凭据引用和 ADR 0042 的鉴权拒绝锁定组成受控轮换路径：Core 公开管理接口先签发继任凭据并使前任失效；旧 Runtime 观察到鉴权拒绝后保留屏障，显式关闭。操作者原子替换私有凭据文件，再用原配置、业务身份、Session 和数据目录启动新 Runtime。当前不在运行中的 SDK 实例上热改 token。

轮换操作与撤销操作的权限不同：公开管理接口要求轮换操作者具有明确委托权，且继任凭据的范围、用途和有效期不能超出授权。测试只在新建的隔离租户内配置该权利，不绕过公开 API 的权限校验，也不由 Bellis 修改 Core 私有数据库。

验证从实际配置文件启动，业务 appInstanceId 取自公开凭据视图。先完成一轮真实 Runtime 决策采用及 Core Usage ACK，再取得未失效的 Context；初始外部事件先追平，避免把已有失效误计作轮换效果。零重叠轮换后旧 Context 必须取消且 readiness 为 503。仅保留旧凭据文件重启必须失败，不能从缓存恢复 Persona。

继任 token 通过当前用户私有文件及同目录原子 rename 替换，配置仍仅保存文件引用。新启动重新协商与读取 live Persona；原 Recall 准备正文、Manifest 和已确认 Usage 逐项保持。继任凭据须接受原 Usage body/身份的重放，并完成新的 Recall。最后公开撤销继任凭据，再次验证 readiness、Context 和本地原事实保持。

这覆盖明确停止/重启、零重叠轮换。重叠期轮换、自动热更新、轮换过程崩溃矩阵、多实例协调和跨进程权限围栏仍需独立验收。保持本地事实或重启就绪不能作为历史缺口解除的依据。

真实 Core/Chromium/启动器/历史恢复联合探针退出 0。原数据中两条 Recall 请求、一条 Manifest 和一条已确认 Usage 逐项保持，新凭据接受原 Usage 重放并完成新 Recall；旧文件启动失败，继任凭据撤销后再次不可用。本轮修改验收脚本与说明，Runtime/Provider 生产源码摘要与此前完整检查基线一致，因此未重复根检查或 24 组恢复冒烟。见 [本轮证据](../evidence/phase4-credential-rotation-probe.json)。
