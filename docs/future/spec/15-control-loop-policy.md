## 15. 游戏控制：本地闭环、策略更新与语义进展

本章描述已授权控制任务内的本地闭环、健康续租、兼容策略更新以及向Bellis报告的语义进展。PolicyUpdate状态机登记在第11.4.16节；Goal、任务图或控制结构变化仍走第10章的交接流程。

### 15.1 观察时效与控制质量

对每类动作分别设有效性条件：高层策略可以依赖较早但仍有效的上下文；点击与快速纠偏使用更严格的观察/页面/变换范围。控制器生成时间和PolicyPatch返回时间不能刷新原始证据年龄。

快照至少关联`capture_instance / frame_id / capture_sequence / captured_at / observed_at / input_context_epoch / transform_version / target_ref / quality`。视觉缓存重复返回同一捕获实例/序号不能冒充新观察；但静态游戏界面可能真的连续多帧像素相同，**不得仅以图像hash未变化判定感知冻结**。采集前进、实际证据年龄、输入后预期变化与服务质量分别核验。

健康报文报告`last_valid_observation`、本地控制进度、最近拒绝原因、输入账目和当前策略有效性。算法运行快但持续读旧帧必须降级；画面新但模型输出不满足当前模式/目标也不能取得输入许可。

### 15.2 本地控制循环

```text
读取仍有效的授权、控制上下文和最新适用观察
→ 先处理接管／安全失效／输入过期
→ 检查当前策略与ControlCapability覆盖
→ 有兼容更新且到边界：完成PolicyUpdate本地切换
→ 当前PolicyBackend选一个有界语义动作/短控制量
→ Interpreter核验坐标/单位/profile并组合ControlFrame
→ Broker检查代次、时效、模式、动作及Effect权限后提交
→ 本地观察效果、进展与停止条件；发布有界语义事件
```

loop自身有界，不能长sleep等动作结束。快策略的推理如果异步执行，结果出口重新校验依据/目标/策略/期限；不能因为模型刚返回就接纳旧动作。连续模式允许多个内部只读估计器，不允许多个最终控制写入者。

目标丢失或无进展时只能执行该能力已注册且在授权内的有限恢复，例如有限镜头重定位；不能自动改成任意探索或无限增大幅度。闭环稳定性、停滞、振荡和目标确认必须测试，频率或线程心跳不能替代这些证据。

### 15.3 continuous_local就绪与持续健康

continuous_local控制器的PREPARED及激活健康条件除进程/模型已加载外，还必须满足：所选控制模式已被当前profile验证；所需观察来源正常；近期可用证据在期限内；动作/模型/映射版本匹配；时限与计算预算可用；本地降级和停止可执行。

本地循环遵循：读取新鲜状态→检查授权/策略/目标/健康→选短动作→合成有界输入→Broker核验→观察效果与进展。没有新高层计划时继续的是**旧有效策略下的新观察闭环**，不是重放旧输入队列。

| 情况 | 合法结果 |
|---|---|
| 云端规划慢／断连，当前授权、策略与观察仍有效 | 已覆盖本地任务继续，不等远端返回 |
| 没有更新的捕获数据，已超过动作允许年龄 | 停止产生不适用动作，撤销/释放或进入已验证有限降级 |
| 画面未变但采集、时效和页面证据正常 | 可以继续waitable状态；不能把像素重复当系统故障 |
| 目标丢失／模式变化 | 只执行已注册的有限恢复；不能持续旧方向直到碰巧成功 |
| 本地策略推理超出控制期限 | 拒绝迟到动作；按明确连续违约阈值降级／接管，不用高频空tick掩盖 |
| 权限失效或人工接管 | 本地先撤权；任何模型结果都不能自动复权 |

任务的瞬时动作、普通战术评分与健康监督可以有不同频率。实际门槛由每能力的TimingContract和完整负载实测确定，不设“任意游戏必须30/60Hz”的全局保证。

### 15.4 有界健康续租

输入续租由游戏本地受信监督链路提出，Broker最终核验；不能由云端LLM、单独WebSocket心跳或只证明线程未退出的定时器续期。至少核验当前Attempt/根owner、监督授权、输入上下文、相关观察时效、控制循环进展及策略仍有效。

新的lease期限不得超过上层授权截止、必要证据有效边界、当前模式安全上限和本地续租窗口的最早者。收到新的“仍健康”消息不能刷新旧证据时间。Broker/看门狗自己使用本地单调时间执行过期释放，不依赖主控线程回来清理。

持键期限与整个任务期限分开。默认以显式后续有效控制帧/健康授权续行；生产端停发、健康失效或观测过期后，Broker清理其负责的合成保持状态与未提交脉冲。无法可靠区分真实与合成输入时使用已验证的接管热键/隔离方案，记录平台限制，不声称能够消除所有物理键冲突。

### 15.5 算法中立的PolicyBackend

| 后端 | 优先考虑的用途 | 验证边界 |
|---|---|---|
| 有限规则／状态机 | 已知UI、剧情推进、可核验基础交互 | 未覆盖页面不猜测，动作后观察 |
| 反馈／跟踪控制 | 已覆盖局部镜头对准与短距离纠偏 | 坐标/目标质量、失锁、振荡和退出条件 |
| 小型学习策略 | 有授权示范与适配数据的局部技能 | 模型/profile兼容、控制时限、偏移场景和真机对照 |
| 局部预测／滚动优化 | 状态可估计、短时输入效果有验证模型的场景 | 模型有效域与不确定性；只执行有限当前部分并重观察 |

不将任何后端名称视为能力证明。特别是MPC返回可行解不能作为游戏成功证据；没有足够状态/预测模型时不要求引入MPC。任何外部实验的速度和成功率都不转换成Bellis、目标显卡或具体游戏的保证。后端接口至少为：接受授权范围/目标/版本化策略与适用观察；返回候选SemanticAction及依据/有效期限/质量；声明资源与失败/停止契约。Backend本身不能签Broker lease，也不能发布未经审核的主播台词。

### 15.6 高层策略请求与本地推理的分工

高层自由策略请求仍由LiveDirector采用并经网关；DomainPlanner只给候选。已批准控制任务内部的PolicyBackend可以连续选择短动作，或在waitable_step中异步请求受限视觉判断，不为每一步回到Bellis主控。

局部模型拿不到主播私有记忆、管理员配置、任意Shell和新增目标权；读取游戏文字也不把其当成控制指令。一次高层推理很慢时本地旧有效策略使用新观察继续；局部模型超出自身时限则按能力降级，不把“不能等主控”解释成“必须不顾质量一直输入”。

### 15.7 兼容PolicyUpdate流程

```text
当前Task/Attempt在有效PolicySnapshot下读取新观察并控制
       │
       ├─ Bellis采用范围受限的PolicyPatch候选
       │      → bridge预登记operation及远端更新引用
       │      → 游戏侧校验基准版本、目标、控制实例、Schema、时效与权限
       │      → 必要资源在旁路准备，不挤占当前闭环
       │      → 到达声明的本地控制边界
       │      → 再校验后切换不可变PolicySnapshot
       │      → 发布实际policy_revision、生效边界与证据
       │
       └─ 候选被拒/过期：旧策略仍有效则继续；旧策略失效则本地降级
```

Bellis使用`propose_policy_patch`请求并取得外部句柄，按事件读取状态，不等待整个控制任务结束。只有Game Runtime能声明实际应用。兼容改参不改变输入根owner、Task或Attempt；结构/目标不兼容则返回明确原因，要求正常计划／控制交接，不能自动扩大修改范围。

### 15.8 PolicyPatch最小契约与验证

| 字段组 | 内容 |
|---|---|
| 归属 | policy_update_id、operation_id、远端game_session、task/attempt、controller_instance、source_owner |
| 基础 | goal_version、base_policy_revision、policy_schema_ref、control_profile_ref、action_schema_ref |
| 内容 | 有限`changes`、候选digest、behaviour_intent、来源与相关证据引用 |
| 有效性 | observed/estimated时间、实际依赖版本、目标主机剩余期限、允许apply_boundary |
| 约束 | 本次次数/费用预算、字段权限、应用后需报告的指标，均受宿主/Runtime上限限制 |

PolicySchema由受信代码/配置定义：每字段类型、单位、上下界、绝对变化限制、按时间变化速率、最小更新间隔、跨字段约束、支持上下文及需验证证据。不是每字段都必须支持同一种限制，但不适用项须明确说明。未知字段、NaN/无穷值、单位不符、冲突组合和越权限修改一律拒绝；不得悄悄裁剪后声称完整采用。若允许建议一个修正候选，必须有新digest并重新走采用/校验。

允许例子是有限的镜头平滑、追击倾向、阅读偏好等行为参数；输入owner、窗口白名单、看门狗、最大无观察输入时限、撤权机制、凭据、禁止动作和普通弹幕非抢占不属于模型可改字段。行为参数只能在外层已授予的安全预算以内起作用。

原始依据与应用时仍相关的上下文都要检查；不把每一张新帧或无关plan_revision当作冲突，也不能仅凭旧base仍相同忽略场景已经不适用。更新进度不重置候选deadline。

### 15.9 应用边界、输入后缀与迟到请求

`policy_revision`针对控制实例单调递增；一次兼容应用使用目标侧受信的条件更新，要求base和相关依赖仍匹配。同基础的多个候选最多一个获准应用；其余明确冲突，不按“最后网络包获胜”。审计可保留拒绝候选，不自动把它改到新base上。

在本地边界固定`effective_control_seq`及新revision：未执行的旧策略相对位移/脉冲后缀失效；已产生效果不回滚。持续保持状态只可在新策略与现有授权都允许的短过渡范围内继承，并由下一合法完整ControlFrame重新确定。新策略不允许的保持状态在边界释放。若控制器无法原子协调其本地策略指针与Broker许可栅栏，先短暂停发新帧直到本地确认；不等待远端LLM，不宣称跨进程同时切换。

不能在同一物理提交过程中切一半新参数一半旧参数。帧、候选和回执都带策略revision/实例，旧revision的迟到帧在生效边界后拒绝。兼容更新只撤销对应控制后缀，不取消无关发言、观察服务或全局Activity。

### 15.10 应用事实、失联与回退

PolicyUpdate状态机唯一登记在第11.4.16节。`RECEIVED / VALIDATED / SCHEDULED`不是应用；只有目标实例已切换、Broker边界建立且可核验时进入`APPLIED`。这仍不表示目标达成。

Bellis失去回执只使外部投影标为stale/unknown，不擅自改变游戏侧状态。目标侧能够查询update_id、当前policy_revision和生效边界；查询不到是否已经生效时记录`UNKNOWN`并只读对账，不重复应用。政策中断不回滚游戏世界。

新参数效果不佳时，返回旧值也必须是以当前revision为base的新受限更新；安全参数从未交给模型修改。已过期/失效的旧策略不能因为“回退”重新获得效力。若新策略已应用但随后本地控制失效，保留APPLIED历史，另报告控制降级/Task结果，不能把更新历史改成从未发生。

### 15.11 控制语义事件

Game Runtime在本地聚合后提供以下有限事件；以下是0.8.0拟议协议的规范名称，字段使用统一Envelope并带`remote_task/attempt/controller_instance/policy_revision/evidence_refs`。策略应用事实身份、查询与遥测规则见第15.13节，不能由插件另起别名。

| 事件 | 可以说明 | 不能说明 |
|---|---|---|
| control.attempt_started | 已在授权范围内开始尝试 | 操作已成功 |
| control.policy_applied | 指定参数revision在目标实例实际应用；唯一应用事实，可去重重放 | RPC已接收或游戏目标达成 |
| control.policy_rejected / control.policy_expired / control.policy_cancelled / control.policy_unknown | 更新真实失败/取消/未知终态，立即结束相应等待 | 已应用、已回滚或整个Task已取消 |
| control.interaction_observed | 当前画面确认进入目标交互状态 | 整个活动已经结束 |
| control.target_lost | 目标关联失效／持续观察缺口 | 目标必然不存在 |
| control.no_progress | 在定义窗口内未出现足够进展 | 必须继续加大输入 |
| control.stage_goal_confirmed | 指定阶段成功证据成立 | 其它目标也已完成 |
| control.degraded / control.takeover_required | 模式能力、健康或时限不足及已执行的降级 | 默认允许主控绕过保护 |

事件按发生实例去重、变化阈值/滞回和最大频率汇总；首次关键故障、撤权与终态不能被普通进度合并丢失。目标坐标每帧变化、每次镜头增量、每个推理Token不直接触发LiveDirector。

“准备采用保守策略”“游戏侧已经应用参数”“画面证实距离增大”是三种不同解说依据。只有经SafetyGate/ContentGuard的正常表达才进入Stage；游戏侧不直接TTS，也不等待解说完成才能完成必要本地控制。

### 15.12 控制与媒体表达的关系

语音Segment解决可审核表达的增量提交；游戏ControlFrame面对持续变化的外部环境，必须按控制TimingContract持续核验。音频已经提交后可沿本地媒体时间播放，不意味着动作宏也能无条件消费全部后缀。

控制策略应用事件仅能支持“策略已调整”的事实表达；可见效果和阶段目标完成分别依据对应证据。任何策略／输入进度解说都走现有双文本审核与Scene，不能由快策略模型直接产生声音。普通弹幕非抢占规则保持；真正的游戏安全或关键剧情事件只按已授权范围处理。

### 15.13 策略更新的全终态通知、查询与时间

PolicyUpdate每个真实终态都通过可靠事件推送：control.policy_applied、control.policy_rejected、control.policy_expired、control.policy_cancelled、control.policy_unknown。control.policy_applied仍是唯一“已应用”事实名；新增失败通知不是第二套应用事件。

每条终态事件包含policy_update_id、operation_id、remote_task_id/remote_attempt_id、controller_instance_id、base_policy_revision、state、实际policy_revision/effective_control_seq（无法确认则null）、reason_code、source_revision与evidence_refs，并使用统一Envelope中的event_id、authority/source_instance和occurred_at。APPLIED必须给出非null实际版本和边界；拒绝/过期/取消必须有原因和“未应用”证明；UNKNOWN不得填写猜测的实际版本。

状态终态、事实身份与Outbox登记在目标Runtime可靠边界固定。重传与查询复用原event_id，不重复计次。Bellis接收时间存投影received_at，与原发生时间分开。[S32] 跨机没有可信时钟映射时只报告同域耗时或含不确定度的区间。

依赖新策略的WaitRegistration订阅该update_id的所有终态：APPLIED继续；REJECTED/EXPIRED/CANCELLED立即以对应结果结束；UNKNOWN立即进入只读核验/人工处理，不能继续傻等applied直到普通超时。旧有效策略和无关聊天按原健康授权继续，不因候选失败被全局停机。

get_policy_update返回权威状态、原终态事实引用和Reconciliation记录。若只是通知丢失，重放原事实；若目标先前已经UNKNOWN终态，后来查明曾应用，追加Reconciliation，不改原终态，也不产生一条伪称“此刻刚应用”的新事件。后继可按契约接受可信应用证据，不接受裸unknown。

cancel_policy_update按第13.8节执行。兼容回退使用新update_id和当前base；不能把取消已应用更新当作回滚游戏世界。APPLYING的有限apply_timeout无法证明确未应用时转UNKNOWN并可靠通知。

### 15.14 视觉、语义和动作的分频计算

DEM把语言和视觉编码与动作生成解耦，并在指令不变时复用语言表示；本项目借鉴计算复用，不把训练任务范围内的结果推广成通用游戏推理能力。[S37]

| 信息／计算 | 触发与缓存 | 仍需单独核验 |
|---|---|---|
| 指令／目标语义 | 指令、Goal、规范化／编码器或实际语义参数变更时重算 | 当前任务仍开放、目的和story_scope允许；命中不续期授权。 |
| 视觉特征／目标状态 | 根据该控制模式要求取得当前根观察；同一root/view可复用编码 | 原始捕获年龄、采集质量、DPI／变换、目标关联。 |
| 动作候选 | 在本地决策边界使用适用观察和语义 | schema/profile、承诺窗口、真实前缀、当前权限。 |
| 安全监督／输入准入 | 独立本地事件或有界周期，实际接纳边界检查 | 不因上面三类缓存命中而跳过。 |

后端没有独立语言表示接口时，不能通过截断模型上下文或重用不兼容KV缓存假装实现DEM。可先缓存经批准的结构化任务描述，或继续使用原模型；优化必须语义等价且有对照。学习型解耦后端只用于已验证技能，剧情理解、自由对话和目标采用仍由原有层次承担。

ComputeReusePolicy及ComputeArtifact落实第4.13节。统计冷启动、warm hit、miss、失效、编码开销和完整负载尾部延迟；缓存优化不能降低内容／隐私／输入安全门槛。

### 15.15 根据最新观察修正未提交候选

Real-Time EXPO-FT把慢动作生成与基于最新观察的快编辑分开；Bellis的对应位置是Game Runtime内部PolicyBackend，而不是要求LiveDirector逐块生成动作。[S36]

```text
慢后端生成behavior_prior候选＋原证据
→ 最新根观察＋当前Goal／profile／policy＋真实ExecutionPrefix
→ 判断原意图仍适用、候选未过期、可修正后缀尚未提交
→ 受限编辑产生新candidate_id（或直接拒绝）
→ 策略范围／数值／时限／安全约束筛选
→ 可选价值函数在合格候选内排序
→ Interpreter → 新ControlFrame → Broker再次核验
```

旧画面可以只作为行为先验的来源，但旧候选的语义适用条件与prior期限仍必须成立。新执行候选明确绑定最新观察和前缀，截止不超过Task、当前grant、该观察和当前TimingContract的最早边界。不得把已过期的可执行命令改时间戳后作为“已修复”复活；不得隐去旧证据使日志看起来一直基于新画面。

目标、模式、profile、Goal或policy发生不兼容变化，前缀有部分提交／UNKNOWN，或剩余时间不足时拒绝编辑。只有位置等该profile允许的连续变化可修正。前缀在编辑期间继续变化时需在输出边界重新校验；没有兼容重基证据即丢弃该结果，不追赶旧序号。

CandidateRepairRecord记录base／输出候选、实际prefix、最新观察、修正policy、started_at／recorded_at、选择／拒绝结果及依据。两时间须同域，差值不超过本次编辑预算；记录结束时间不能作为新的捕获时间。质量分数不是安全概率；Q值不能取消Schema、lease、Effect或监督限制。无合格候选时走已登记降级／释放／接管，不用原候选兜底强行执行。

只有模型修正实际改善任务且完整直播负载可达标时才启用。规则式纠偏可先在C1测试；采用训练的编辑／价值网络还需C4的数据许可、离线验证和制品批准。公开直播不在线更新权重。

### 15.16 后端选择与不过度组合

首个固定剧情界面优先采用简单适配或单次定位；连续控制先采用可验证的规则／反馈或单一快速后端。语义复用可作为这些后端内部优化，不必先安装专用小模型。

只有当简单后端不能满足覆盖、质量或时限，而慢策略仍提供可测收益时，才评估“慢候选＋快修正”。解耦策略与执行前修正是可比较、可组合但互不强制的路线。更换路径需要Manifest明确支持、资源准入和安全边界，不在运行中临时拼接陌生模型。

一段连续控制并非同时调用定位重排、VLA、编辑器、价值函数和反思审查。后端profile列出实际启用的链路；不启用的契约保持disabled，失败也不能绕回没有Broker约束的通用电脑Agent。
