## 10. 结构性更新、检查点与恢复

### 10.1 三类更新

| 更新对象 | 处理 | Task／Attempt |
|---|---|---|
| 兼容行为参数 | PolicyUpdate：字段/单位/范围/变化/组合约束校验，在本地控制决策边界应用（第15.7–15.10节） | 不默认暂停，不默认新Attempt，不释放根输入owner |
| Goal、任务图、控制结构／不兼容策略 | 影响分析、受影响检查点、必要清理、Plan／授权交接 | 依第10.3–10.4节保留或新建；不是普通PolicyPatch |
| 源码、模型权重、输入格式／不兼容profile | 离线质量与兼容验收、受控停用、新实例、重新授权 | 不热替换在途后端，不恢复旧键鼠或PCM |

“参数兼容”由受信ControllerManifest、PolicySchema和实际状态判定，不由模型自报。新目标、改变角色/界面控制模式、扩大资源处置或修改安全阈值不能伪装为兼容参数。

静态Plan先行，局部在线修订后实现；持续控制可先使用固定有效策略验证，再启用兼容调参。“不停机调参”是本设计的取舍，不是任何已验证的外部实现能力；采用的方式是继续旧有效闭环，不在等待高层返回期间冻结全部动作。

### 10.2 Checkpoint与ResumeTicket

Checkpoint与ResumeTicket的字段登记在附录B.6：检查点含所属Task/Attempt、种类、到达时间、受影响资源、未决效果、上下文约束、可兼容参数类型、快照引用与过期时间；票据另绑定Goal/Plan、依赖与控制器版本、允许恢复范围和旧Attempt。

检查点是可解释的暂停/交接边界，不保证游戏时间停止，也不自动证明清理完成。ResumeTicket在必要清理和快照核验后签发，绑定Goal/Plan、关键依赖、控制器版本、现场证据、旧Attempt和允许恢复范围。

不保存原始待发按键、整段未播PCM或可复用旧租约。游戏导航保存剩余语义目标与路线依据；直播活动保存已完成节点、业务结果和未决依赖；原发言被安全中止后不得靠恢复票据从头重播。

### 10.3 结构性局部计划提交流程

本节只用于Goal／任务图／控制结构等需要交接的变更；第15.7节的兼容参数更新不机械执行下面的停发、Settlement与新Attempt步骤。

1. 登记`candidate_id / base_revision / change_scope / digest`，静态校验图和预算。
2. 计算保留、取消、新增、参数修改与失效后继；兼容性不能只看稳定ID。
3. 旁路准备必要资源，不能取得正式输入/播出权，也不能挤满前台额度。
4. 只等待受影响Task到检查点；无关观察服务、其它Activity与正在安全播放的无关表达继续。
5. 受影响控制器停发、撤销尾部；必要资源清理与交接确认。
6. 再检查base_revision、目标、证据年龄、affordances、权限和未决Effect。
7. 在本地权威事务边界更新ActivePlanRef与映射，并记录待发送操作。
8. 外部Runtime按自己的计划/授权机制接受；经回执确认实际应用，不以本地事务冒充远端已生效。

候选冲突或过期后拒绝/重新提出，不偷偷改旧候选基础版本。更新失败不意味着游戏世界回滚；可恢复旧策略时也必须使用当前实际状态。

### 10.4 暂停与恢复

Task支持暂停时先`QUIESCING`，取得语义检查点、旧Attempt产生SUSPENDED结果并完成Settlement，再Task进入PAUSED。未派发Task可以直接PAUSED。暂停期间必要观察服务继续。

恢复先校验ticket、Goal、能力、证据、监督授权与资源；统一创建新Attempt，旧SUSPENDED Attempt保持终态。兼容且从未暂停的保留Task继续原Attempt，不因plan_revision变更全局撤权。

不支持恢复的任务只能停止并让主控创建新的明确业务工作。暂停到界超时走checkpoint_timeout；安全条件失效或控制器拒绝/无法静默时按stop路径处理。两种情况都先本地撤权，再进入STOPPING，效果不明时进入RECONCILING，不伪报暂停成功。

### 10.5 范围与崩溃窗口

记录`prepared / checkpoint_requested / quiesced / local_committed / remote_accepted / remote_applied / reconciled`等事实及operation关联，不把它们当作跨端共同状态机。主机/Stage/Broker重启产生新实例和授权代次；旧输入与媒体许可作废。

本地提交前崩溃：无执行许可的候选可回收，但已提交远端效果仍需对账。本地提交后回执丢失：先查外部operation/活动状态，不重复启动。不能从持久化按键或媒体字节队列直接恢复副作用。

### 10.6 恢复层级与升级

近端适配有限重试→控制器重观察/恢复→Task重规划→主控活动修订→人工接管。沿同一recovery_budget_id累计次数/费用/时间；安全撤权、隐私拒绝、未决效果可跳过前几层直接请求人工。

恢复只能扩大已知状态，不能扩大授权。操作员接管后的复权需要明确操作与现场重识别；新弹幕、重连和LLM返回都不能自动夺回控制。

### 10.7 恢复控制：何时、何处与保留什么

RIR将恢复组织为when／where／what三项联动选择；本设计借鉴这一区分，不假定Bellis拥有论文环境的任意可恢复状态。[S38]

| 问题 | Bellis规范 |
|---|---|
| when：何时审查 | 来源Attempt失败、达到有界无进展窗口、重复错误／状态循环、显式恢复请求；配置可选自适应审查，但上下限与总调用预算固定。 |
| where：从哪里继续 | 只在RecoveryCapability声明、当前仍有效且有真实恢复证据的边界中选择；先排除越权／不可清理范围，再比较损失的进度与修复效果。 |
| what：保留什么 | Goal与Journal继续作权威；筛选ReflectionRecord中的可复用条目，清除被恢复失效的当前状态陈述，并应用story_scope／隐私过滤。 |

RecoveryReviewPolicy规定触发窗口、最小间隔、最多待处理请求、审查调用／Token预算、每次最多候选检查点、超时和默认出口。默认不做逐帧LLM审查；重复信号按Task/Attempt与失败发生实例合并。审查可决定维持仍有效的原任务、产出RecoveryProposal、重建受限上下文或请求人工；这些决定记录在相应Task结果与已登记产物中，不新增一套未登记命令。静态不支持通过固定错误原因表达。

安全失焦、撤权、lease过期和未知效果不等审查。审查超时或不可用时，未完成的原任务按既有期限／失败政策处理；不能为等诊断继续输入或无限暂停。首次P3可只记录失败信息，P6才启用自动恢复审查和恢复上下文采用。

### 10.8 恢复能力与保护范围

Checkpoint保存可解释的语义边界；只有配套RecoveryCapability声明并验证的范围才是可恢复环境。每种能力固定方法、目标scope、可恢复对象、不可恢复对象、验证契约、必要授权与时间／次数上限。

| method | 允许改变什么 | 执行约束 |
|---|---|---|
| context_rebuild | 重新组织当前Goal、当前观察与合法反思的计算上下文 | 不改变世界；不恢复旧输入或重写历史。 |
| compensating_action | 当前授权范围内的新补偿动作，如退出本次打开的菜单 | 独立Action及必要Effect；这是后续新动作，不是抹除前次效果。 |
| sandbox_snapshot | 已验证隔离沙箱内的显式白名单状态 | 不包含宿主安全／业务账本；快照内容、版本和恢复结果必须核验。 |
| game_save | 目标Game Pack真实支持的特定游戏存档范围 | 有限操作、明确批准与验证；读档UI输入仍经过Broker，不能任意文件／Shell操作。 |

以下保护范围一律不进入世界恢复：已提交操作与Effect账本、Settlement与未知墓碑、公开音视频事实、Outbox投递历史、安全／监督／grant／lease、删除墓碑、累计费用和恢复预算。禁止把整个Bellis数据库或进程内存恢复到早期快照。游戏资源本身可能随读档变化，但过去的消费／点击记录不能删除；若需要新的业务意图，须有真实新发生范围与授权，而不是复用旧semantic_key。

不支持相应方法返回RECOVERY_METHOD_UNSUPPORTED；回滚请求不能自动改成stop再假称restore成功。game_save只说明有可执行方法，当前存档是否适用、能否保持剧情边界、能否隔离旧操作，仍需执行前验证。

### 10.9 从恢复提议到新尝试

```text
失败事实／停滞信号 → 有界审查 → RecoveryProposal（无执行权）
→ 校验目标、scope、能力、检查点、原预算和保护范围
→ 关闭受影响旧Attempt的新增效果准入，核对Effect与必要清理
→ 按现有采用流程登记完整恢复Action及必要Effect
→ 目标Runtime执行获准方法 → 新现场核验／恢复证据
→ RecoveryResult＋新当前观察＋受限RecoveryContextView
→ 对仍开放的Task创建新Attempt；终态Task则另建明确的新Task
```

恢复Action的资源owner与原执行者不能互相等待：先清理或按已有受限委托完成交接，再取得恢复所需资源。旧操作仍可能生效时不得恢复后启动冲突输入；行政结案只有在第7.8节满足实际隔离与新范围条件后才可能允许继续。

同一个Task仍开放、目标与允许效果不变时，恢复保留task_id并创建新attempt_id；Task已FINISHED时不复活，建立supersedes_task_id关系的新Task，并延用原recovery_budget_id。同一effect_intent_id的自动重执行仍必须证明无效果且已清理；读档不自动构成这种证明。

源端恢复失败但效果范围已知，按真实FAILED／EXPIRED等结果收尾；恢复提交后无法确认是否发生则UNKNOWN并只读对账，不自动再读档。RecoveryResult的SUCCEEDED必须同时满足该方法的恢复后置条件与必要清理，不等于原Goal已经成功。

### 10.10 恢复后上下文、崩溃与预算

世界恢复不会倒拨宿主单调时钟、capture/source序号或任何安全epoch。由真实变化的权威推进input_context_epoch、必要transform_version和story_scope；没有变化的scope不全局递增。读档后的截图是新捕获，旧GroundingResult、视觉缓存、旧执行候选与租约均不能直接复用。

RecoveryContextView分别引用当前Goal、恢复后的当前观察、必要历史Attempt摘要和通过筛选的反思项。当前状态由新观察生成，过去失败分支不含当前状态写权限。上下文更新替换同一用途的有限视图，不无限追加反思Prompt；解释很长时先保留失败事实、未决限制和下次行动所需约束。

所有审查、模型费用、补偿、快照恢复和新Task继续计入原总预算。截止已过只允许清理／对账，不得借恢复获得新的业务时间；需要延长目标须显式采用新授权范围并保留累计账目。崩溃重启先恢复保护平面的最新记录和删除墓碑，再核对端点；没有可靠证据则保持相关能力关闭。
